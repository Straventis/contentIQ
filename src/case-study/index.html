Section 01

The Opportunity & Data Hypothesis

The Problem

LinkedIn's native analytics are a snapshot, not a ledger

Every metric LinkedIn shows a creator reflects a live, cumulative total. There is no native way to see yesterday's number once today overwrites it — no historical delta, no way to answer "how did this post's engagement actually change over the two weeks since I published it" without manually exporting the data before it disappears.

For content produced as a professional discipline rather than a hobby, that is a real operational gap. You cannot systematically improve what you cannot observe changing over time, and LinkedIn's own interface is architected to make that observation impossible past a single day.

The Product Hypothesis

Persistent history unlocks positioning insight a snapshot never can

If post-level and account-level metrics were captured on a recurring cadence and stored as an immutable time series — not a live number that overwrites itself — the resulting historical record would surface patterns invisible in any single point-in-time view.

Which content pillars compound differently over weeks, not just which post did best today. Whether a spike in reach was a one-hour flash or a two-week slow build. Real week-over-week momentum, measured against the actual prior period, not a static number that only ever moves in one direction.

  • Multi-source ingestion, decided on evidence, not convenience. Rather than lock into LinkedIn's own official API — which requires Marketing Developer Platform partner approval, a process structurally built for companies serving many customers, not one person's personal dashboard — three third-party providers were evaluated against a specific, checkable criterion: which one is a confirmed official LinkedIn Analytics API launch partner, not just a tool with an unclear terms-of-service standing. Buffer confirmed as a day-one official partner directly from their own public blog; a competing tool's access method could not be confirmed as sanctioned, with a documented history of prior enforcement action tied to how similar tools access LinkedIn data. That evidence, not brand familiarity, decided the primary source.
  • AI classification built for vendor risk from the start. The pillar-tagging classifier was originally a single-provider integration. Mid-build, it began failing in production with a 401 authentication error that traced back to a genuine, current, external Google platform bug — newly issued API keys were being broadly rejected by Google's own backend, confirmed against multiple independent reports on Google's own developer forum, unrelated to any application code. Rather than wait on an unscheduled third-party fix, the classifier was rearchitected around a pluggable provider registry, with Claude and OpenAI ready as same-day fallbacks behind one line of config. Any single-vendor AI dependency is a single point of failure; the fix cost one refactor, not a redesign.
  • Engagement rate normalized consistently across every source. Reactions, comments, and shares arrive from different providers on different schedules and in different shapes. Every merge script normalizes to the same engagement-rate definition before it ever reaches the dashboard, so switching the active data source never silently changes what a number means.

Real production bugs found and fixed, not glossed over

GitHub's own documented behavior — commits pushed using the default repository token cannot trigger other workflows — silently blocked the entire automated refresh pipeline from ever reaching the live site for its first days in production.

Buffer's own feed was found to return genuine near-duplicate entries for the same real post, sometimes twenty seconds apart, requiring deduplication before matching rather than after.

A missing dependency-install step caused the AI classifier to fail on every scheduled run while the rest of the pipeline reported success — hidden by an unrelated log-ordering quirk in how the CI environment buffers subprocess output.

Pivot highlight

Why V4.0 (Direct LinkedIn API) was deferred, and how the roadmap pivoted around it. LinkedIn's Marketing Developer Platform approval process runs four weeks to four months and is designed for companies building products for many customers — not for evaluating a single person's personal dashboard. There was no committed timeline, and no way to force one.

Rather than block the entire roadmap on an external approval outside the team's control, V2.0's scope was deliberately widened past the original two-tab redesign to build a swappable, config-driven multi-source architecture instead — Buffer as primary, Taplio as a working fallback, Zernio next in line. A provider's terms-of-service change, price increase, or outage no longer takes the product down; switching sources is a one-line config change, not a rewrite. What began as a blocked task is the direct reason V2.0 grew into a fully automated pipeline instead of shipping as originally scoped.
